# Документация проекта URL Shortener

## 1. Назначение проекта

Проект реализует сервис сокращения ссылок. Пользователь передает исходный адрес, сервис создает короткий код, а затем по этому коду выполняет перенаправление на исходный адрес.

Система ориентирована на исследование производительности при высокой доле операций чтения. Основной рабочий сценарий: много переходов по уже созданным коротким ссылкам и сравнительно небольшое число созданий новых ссылок.

Ключевые требования текущей версии:

- принимать адреса как с протоколом, так и без него;
- хранить исходные данные в PostgreSQL;
- ускорять чтение через Redis;
- при переходе продлевать срок действия ссылки так, чтобы оставшийся срок снова становился равен 7 дням;
- сохранять перенаправления даже при отказе Redis, пусть и с большим временем обработки;
- выполнять накопление переходов и продлений срока в Redis с последующей пакетной записью в PostgreSQL;
- предоставлять метрики для Prometheus и панели Grafana на русском языке;
- поддерживать подготовку данных, прогрев и нагрузочные испытания.

## 3. Общая архитектура

Приложение выполнено как один серверный модуль Spring Boot. Внешние системы развертываются рядом через Docker Compose.

```text
Пользователь или генератор нагрузки
        |
        v
Spring Boot приложение
        |
        +-- PostgreSQL: постоянное хранение ссылок
        |
        +-- Redis: быстрое чтение ссылок и временное накопление изменений
        |
        +-- /actuator/prometheus: выдача метрик
                    |
                    v
              Prometheus -> Grafana
```

PostgreSQL является основным источником данных. Redis используется как ускоряющий слой и как промежуточное хранилище для переходов и продлений срока действия. Если Redis недоступен, приложение продолжает выполнять перенаправления через PostgreSQL.

## 4. Основные модули приложения

### 4.1. `LinkController`

Контроллер принимает внешние HTTP-запросы:

- `POST /api/v1/shorten` - создание короткой ссылки;
- `GET /api/v1/{shortCode}` - перенаправление по короткому коду.

Контроллер не содержит основной логики. Он проверяет входные данные через валидацию, вызывает служебный слой и формирует HTTP-ответ.

### 4.2. `LinkService`

Содержит основную логику работы со ссылками:

- нормализует и проверяет исходный адрес;
- создает короткий код;
- ищет уже существующую активную ссылку для того же адреса;
- сохраняет новые ссылки в PostgreSQL;
- записывает ссылку в Redis;
- читает ссылку из Redis;
- при отсутствии данных в Redis читает ссылку из PostgreSQL;
- передает сведения о переходе в `LinkAccessBuffer`.

Если адрес передан без протокола, например `example.com`, он приводится к виду `http://example.com`. Допускаются только `http` и `https`.

### 4.3. `LinkAccessBuffer`

Компонент накапливает сведения о переходах и продлении срока действия ссылки.

При каждом успешном переходе:

- увеличивается счетчик переходов в Redis;
- вычисляется новая дата окончания действия ссылки;
- запись ссылки в Redis обновляется с новым сроком;
- изменение срока помещается во временное хранилище Redis.

Раз в 30 секунд компонент выполняет пакетную запись накопленных изменений в PostgreSQL:

- прибавляет накопленные переходы к `click_count`;
- обновляет `expires_at`.

Такой подход уменьшает число операций записи в PostgreSQL при большой нагрузке. При этом перенаправления остаются быстрыми, а постоянное хранилище обновляется не при каждом переходе, а пачками.

### 4.4. `RedisHealthTracker`

Хранит текущее состояние доступности Redis внутри приложения. Если операция с Redis завершается ошибкой, компонент помечает Redis как недоступный. После этого основной путь чтения сразу идет в PostgreSQL, не тратя время на повторные неудачные обращения к Redis в каждом запросе.

### 4.5. `RedisRecoveryTask`

Периодически проверяет, восстановился ли Redis. Интервал проверки задается параметром `app.redis-probe-interval-ms` и по умолчанию равен 5 секундам.

### 4.6. `LinkCleanupTask`

Периодически удаляет просроченные ссылки из PostgreSQL. Интервал задается параметром `app.cleanup-interval-ms` и по умолчанию равен 1 часу.

### 4.7. `GlobalExceptionHandler`

Формирует единый вид ответов при ошибках:

- ошибка проверки входных данных;
- неправильный формат адреса;
- внутренняя ошибка приложения.

Сообщения об ошибках выдаются на русском языке.

## 5. Модель данных

Основная таблица: `links`.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `BIGSERIAL` | Внутренний идентификатор записи |
| `short_code` | `VARCHAR(16)` | Короткий код ссылки |
| `original_url` | `TEXT` | Исходный адрес |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | Время создания |
| `expires_at` | `TIMESTAMP WITH TIME ZONE` | Время окончания действия |
| `click_count` | `BIGINT` | Счетчик переходов |

Индексы:

- уникальный индекс по `short_code`;
- индекс по `original_url`;
- индекс по `expires_at`.

`original_url` не является уникальным. Это нужно для корректного поведения после истечения срока действия: если старая ссылка уже просрочена, можно создать новую ссылку для того же исходного адреса.

## 6. Данные Redis

Redis используется для трех видов данных.

### 6.1. Быстрое чтение ссылки

Ключ:

```text
link:{shortCode}
```

Значение хранится в виде JSON:

```json
{
  "url": "https://example.com",
  "expiresAt": "2026-05-27T12:00:00Z"
}
```

Срок жизни ключа соответствует оставшемуся сроку действия ссылки.

### 6.2. Накопление переходов

Ключ:

```text
links:clicks:buffer
```

Это хранилище вида `shortCode -> количество переходов`. Оно используется для последующей пакетной записи счетчиков в PostgreSQL.

### 6.3. Накопление продлений срока

Ключ:

```text
links:expiry:buffer
```

Это хранилище вида `shortCode -> новая дата окончания действия`. Если по одной ссылке за 30 секунд было много переходов, в PostgreSQL достаточно записать последнюю дату окончания действия.

## 7. Правило срока действия ссылки

Начальный срок действия ссылки равен 7 дням.

При каждом успешном переходе срок действия продлевается так, чтобы оставшийся срок снова стал равен 7 дням.

Пример:

- ссылка создана 1 мая и действует до 8 мая;
- 3 мая по ней перешли, до окончания оставалось 5 дней;
- после перехода срок действия снова становится 7 дней;
- новая дата окончания действия - 10 мая.

В базе данных и Redis это правило хранится как абсолютная дата `expires_at` или `expiresAt`, вычисленная от момента перехода.

## 8. Основные сценарии работы

### 8.1. Создание короткой ссылки

1. Клиент отправляет `POST /api/v1/shorten`.
2. Приложение очищает строку от лишних пробелов.
3. Если протокол не указан, добавляется `http://`.
4. Адрес проверяется на корректность.
5. Выполняется поиск активной ссылки с таким же исходным адресом.
6. Если активная ссылка найдена, возвращается ее код.
7. Если активной ссылки нет, создается новая запись в PostgreSQL.
8. Новая ссылка записывается в Redis.
9. Клиент получает короткий код.

Такое поведение делает создание активной ссылки для одного адреса повторяемым: повторный запрос возвращает существующий короткий код, пока ссылка не просрочена.

### 8.2. Переход по короткой ссылке при доступном Redis

1. Клиент отправляет `GET /api/v1/{shortCode}`.
2. Приложение ищет запись `link:{shortCode}` в Redis.
3. Если запись найдена и не просрочена, исходный адрес возвращается клиенту через ответ `302`.
4. Сведения о переходе записываются в Redis.
5. Срок действия ссылки в Redis становится равен 7 дням от момента перехода.
6. Изменения для PostgreSQL накапливаются и записываются пачкой раз в 30 секунд.

### 8.3. Переход при отсутствии записи в Redis

1. Клиент отправляет `GET /api/v1/{shortCode}`.
2. В Redis записи нет или запись повреждена.
3. Приложение читает ссылку из PostgreSQL.
4. Если ссылка найдена и не просрочена, клиент получает перенаправление.
5. Сведения о переходе записываются в Redis для последующей пакетной записи.

### 8.4. Переход при отказе Redis

1. Приложение помечает Redis как недоступный.
2. Следующие запросы сразу обращаются к PostgreSQL.
3. Перенаправления продолжают работать.
4. Накопление счетчиков и продлений через Redis временно невозможно.
5. Фоновая проверка раз в 5 секунд определяет восстановление Redis.

Главный приоритет при таком отказе - сохранить возможность переходов по ссылкам. Счетчики переходов являются внутренней метрикой, поэтому небольшая потеря счетчиков при отказе Redis считается допустимой.

## 9. HTTP API

### 9.1. Создание ссылки

Запрос:

```http
POST /api/v1/shorten
Content-Type: application/json
```

Тело:

```json
{
  "url": "example.com/page"
}
```

Также допустимо:

```json
{
  "url": "https://example.com/page"
}
```

Успешный ответ:

```http
201 Created
Location: /api/v1/abc123
```

Тело ответа:

```json
{
  "shortCode": "abc123"
}
```

Ошибки:

- `400 Bad Request` - пустой адрес или неправильный формат;
- `500 Internal Server Error` - внутренняя ошибка приложения.

### 9.2. Переход по ссылке

Запрос:

```http
GET /api/v1/abc123
```

Успешный ответ:

```http
302 Found
Location: https://example.com/page
```

Ошибки:

- `404 Not Found` - ссылка не найдена или просрочена.

## 13. Нагрузочные испытания

Нагрузочные испытания находятся в каталоге `load-tests`.

Файлы:

- `methodology_test.js` - сценарии k6;
- `run.sh` - точка входа для запуска из Bash;
- `run.py` - подготовка данных, прогрев и запуск сценариев;
- `seed.sql` - заполнение PostgreSQL тестовыми ссылками.

Перед каждым основным испытанием рекомендуется выполнять подготовку данных и прогрев. Это уменьшает влияние холодного запуска, пустого Redis, первичного заполнения соединений и начальной работы виртуальной машины Java.

### 13.1. Подготовка данных

По умолчанию создается 100000 ссылок. Запуск выполняется через `run.sh`, который вызывает Python-скрипт `run.py`.

Поддерживаются два режима подготовки данных:

- `docker` - локальный режим для машины, на которой запущены контейнеры PostgreSQL и Redis. Скрипт очищает Redis, пересоздает тестовые данные через `seed.sql`, создает списки кодов и после прогрева очищает буферы Redis.
- `postgres` - удаленный режим для отдельной машины генератора нагрузки. Скрипт подключается к PostgreSQL через `psql`, выполняет `seed.sql`, создает списки кодов и затем прогревает популярные ссылки через HTTP API приложения. В этом режиме не нужен Docker на машине генератора, но нужен сетевой доступ к PostgreSQL.

Режим `auto` используется по умолчанию: при локальном `BASE_URL` (`localhost` или `127.0.0.1`) и найденных контейнерах PostgreSQL/Redis выбирается `docker`, иначе выбирается `postgres`.

Важно: удаленный режим `postgres` пересоздает данные в PostgreSQL, но не очищает Redis напрямую. Если нужно строго очистить Redis перед испытанием, используйте локальный режим `docker` на сервере или очистите Redis вручную.

Распределение чтения в испытаниях: 80 процентов запросов идут по популярным ссылкам, 20 процентов - по остальным. Это ближе к реальному использованию, чем равномерный случайный выбор.

| Переменная | Значение по умолчанию | Назначение |

| `SCENARIO` | выбирается в меню | Сценарий испытания |

| `FAILOVER_STOP_AFTER` | `120` | Через сколько секунд остановить Redis в сценарии отказа |
| `FAILOVER_DOWN_SECONDS` | `180` | Сколько секунд держать Redis остановленным |

### 13.3. Сценарии

Доступные сценарии:

- `warmup` - прогрев перед измерениями;
- `nominal` - номинальная нагрузка;
- `capacity` - поиск предельной пропускной способности;
- `stress` - стрессовое испытание;
- `soak` - длительное испытание стабильности;
- `failover` - работа при отказе Redis.

### 13.4. Запуск на той же машине

В среде с Bash:

```bash
cd load-tests
./run.sh
```

Если `BASE_URL` указывает на `localhost` и контейнеры `shortener-db` и `shortener-redis` запущены на этой же машине, режим `auto` выберет быструю подготовку через Docker и PostgreSQL.

Или с явным выбором сценария:

```bash
cd load-tests
SCENARIO=nominal ./run.sh
```

Если приложение запущено на этой же машине, но прямой доступ к Docker не нужен или недоступен, можно явно выбрать подготовку через обычный клиент PostgreSQL:

```bash
cd load-tests
BASE_URL=http://localhost:8080 PREPARE_MODE=postgres PGPASSWORD=postgres SCENARIO=nominal ./run.sh
```

### 13.5. Запуск с другой машины в локальной сети

На машине с генератором нагрузки должны быть установлены Python 3.8 или новее, k6 и клиент `psql`. Docker на машине генератора не требуется.

Для подготовки данных через PostgreSQL, прогрева через API и запуска сценария нужно указать адрес сервера с приложением и параметры подключения к PostgreSQL:

```bash
cd load-tests
BASE_URL=http://192.168.1.10:8080 PREPARE_MODE=postgres PGHOST=192.168.1.10 PGPASSWORD=postgres SCENARIO=nominal ./run.sh
```

Если PostgreSQL доступен по строке подключения, можно использовать `POSTGRES_DSN`:

```bash
cd load-tests
BASE_URL=http://192.168.1.10:8080 PREPARE_MODE=postgres POSTGRES_DSN=postgresql://postgres:postgres@192.168.1.10:5432/shortener SCENARIO=nominal ./run.sh
```

Если данные уже подготовлены на сервере, можно отключить подготовку. В этом случае на машине генератора должны быть актуальные файлы `shortcodes.txt` и `shortcodes_popular.txt`:

```bash
cd load-tests
BASE_URL=http://192.168.1.10:8080 PREPARE_DATA=false SCENARIO=nominal ./run.sh
```

При запуске с другой машины важно, чтобы файлы `shortcodes.txt` и `shortcodes_popular.txt` соответствовали данным, загруженным в PostgreSQL.

В сценарии `failover` удаленный генератор нагрузки по умолчанию не управляет Redis, потому что у него нет локального контейнера Redis. Остановку и запуск Redis нужно выполнить на сервере вручную либо запускать сценарий на сервере в локальном Docker-режиме.

### 13.6. Результаты испытаний

После выполнения создаются файлы:

- `report_{scenario}_{time}.html` - отчет в виде страницы;
- `summary_{scenario}_{time}.json` - краткая сводка в JSON.

Для сравнения результатов между запусками нужно фиксировать:

- сценарий;
- адрес генератора нагрузки;
- число подготовленных ссылок;
- длительность прогрева;
- настройки приложения;
- состояние Docker Desktop;
- загрузку процессора и памяти;
- показатели Grafana.

## 14. Наблюдаемость

Приложение публикует метрики через:

```text
/actuator/prometheus
```

Prometheus забирает метрики и передает их в Grafana. Панели Grafana переведены на русский язык.

Основные группы метрик:

- HTTP-запросы;
- время обработки запросов;
- состояние Redis;
- успешность чтения из Redis;
- ошибки Redis;
- размер временных хранилищ переходов и продлений;
- число записанных переходов;
- число записанных продлений срока;
- длительность пакетной записи;
- состояние JVM;
- состояние PostgreSQL и соединений.

Для анализа испытаний особенно важны:

- число запросов в секунду;
- 95-й процентиль времени ответа для переходов;
- 95-й процентиль времени ответа для создания ссылок;
- доля ошибок;
- размер временных хранилищ Redis;
- задержка пакетной записи в PostgreSQL;
- поведение при отключении Redis.

## 15. Проверка качества

Модульные и слойные проверки запускаются командой:

```powershell
mvn test
```

Сборка без запуска проверок:

```powershell
mvn -DskipTests compile
```

Для выполнения этих команд локальная среда должна использовать Java 21. Если Maven запускается на Java 11, сборка завершится ошибкой вида `release version 21 not supported`.

## 16. Поведение при отказах

### 16.1. Redis недоступен

Ожидаемое поведение:

- перенаправления продолжают выполняться через PostgreSQL;
- время ответа увеличивается;
- чтение из Redis временно отключается;
- после восстановления Redis приложение возвращается к обычному режиму;
- часть внутренних счетчиков переходов может быть потеряна.

### 16.2. PostgreSQL недоступен

Ожидаемое поведение:

- создание новых ссылок невозможно;
- ссылки, уже находящиеся в Redis, могут перенаправляться до истечения срока ключей;
- пакетная запись переходов и сроков в PostgreSQL будет завершаться ошибками.

PostgreSQL является главным хранилищем данных, поэтому его отказ является критичным.

### 16.3. Приложение перезапущено

После перезапуска:

- постоянные данные остаются в PostgreSQL;
- Redis может сохранить или потерять временные данные в зависимости от настроек контейнера;
- невыполненная пакетная запись из Redis может быть потеряна, если Redis также был очищен.

## 17. Ограничения текущей версии

Текущая версия сознательно оставляет часть возможностей вне реализации:

- нет распределенного согласования между несколькими экземплярами приложения;
- Redis не используется как надежная очередь с подтверждением обработки;
- небольшая потеря внутренних счетчиков переходов допустима;
- нет ограничения частоты запросов для отдельных клиентов;
- нет отдельного пользовательского интерфейса;
- нет авторизации и личных кабинетов;
- нет пользовательской настройки срока действия ссылки;
- нет отдельного хранилища подробной истории переходов.

Эти ограничения допустимы для исследовательского прототипа, где главная цель - оценить влияние Redis, пакетной записи и прогрева на производительность перенаправлений.

## 18. Типовые проблемы и решения

### 18.1. Docker Compose не запускается

Проверьте, что Docker Desktop запущен. Затем выполните:

```powershell
docker version
```

Если клиент Docker установлен, но сервер недоступен, нужно запустить Docker Desktop и дождаться полной готовности.

### 18.2. Maven сообщает `release version 21 not supported`

Причина: Maven запущен на Java ниже 21.

Проверьте версию:

```powershell
java -version
mvn -version
```

Нужно установить Java 21 и убедиться, что Maven использует именно ее.

### 18.3. Grafana не показывает данные

Проверьте:

- запущен ли Prometheus;
- доступна ли страница `http://localhost:9090/targets`;
- есть ли цель приложения в состоянии `UP`;
- доступна ли страница `http://localhost:8080/actuator/prometheus`.

### 18.4. Нагрузочный скрипт не находит короткие коды

Возможные причины:

- не была выполнена подготовка данных;
- PostgreSQL недоступен;
- `seed.sql` завершился ошибкой;
- файлы `shortcodes.txt` и `shortcodes_popular.txt` не созданы или не соответствуют текущей базе.

### 18.5. Старый том PostgreSQL содержит прежний уникальный индекс

В новой схеме `original_url` не должен быть уникальным. Для старой базы предусмотрено изменение схемы, которое удаляет прежний уникальный индекс.

Если локальная база находится в нерабочем состоянии и ее данные не нужны, можно полностью пересоздать тома:

```powershell
docker compose down -v
docker compose up -d --build
```

Команда `docker compose down -v` удаляет данные PostgreSQL, поэтому ее нельзя выполнять, если эти данные нужно сохранить.

## 19. Связь с нагрузочными испытаниями

Текущая архитектура поддерживает более реалистичную методику испытаний:

- перед измерениями выполняется прогрев;
- данные предварительно заполняются большим набором ссылок;
- популярные ссылки прогреваются отдельно;
- чтение распределяется по схеме 80/20;
- Redis можно отключить во время испытания и проверить сохранение перенаправлений;
- результаты сохраняются в виде файлов отчета и сводки;
- Grafana показывает внутреннее состояние приложения во время испытания.

При анализе результатов важно разделять:

- производительность обычного режима с Redis;
- производительность режима без Redis;
- задержку создания ссылок;
- задержку перенаправлений;
- задержку пакетной записи;
- ошибки генератора нагрузки;
- ограничения машины, на которой запускается генератор.

## 20. Рекомендуемый порядок демонстрации проекта

1. Запустить систему через Docker Compose.
2. Проверить состояние приложения через `/actuator/health`.
3. Открыть Grafana и убедиться, что панели получают данные.
4. Выполнить подготовку данных на 100000 ссылок.
5. Выполнить прогрев.
6. Запустить номинальное испытание.
7. Зафиксировать показатели времени ответа и ошибок.
8. Запустить испытание с отказом Redis.
9. Показать, что перенаправления продолжают работать.
10. Сравнить показатели обычного режима и режима отказа.

## 21. Краткое описание текущего технического решения

Сервис сокращения ссылок построен на Spring Boot и использует PostgreSQL как основное хранилище. Redis применяется для ускорения чтения популярных ссылок и для накопления изменений, возникающих при переходах. При каждом переходе срок действия ссылки снова становится равен 7 дням, а счетчик переходов и новый срок записываются в PostgreSQL пакетно раз в 30 секунд. При отказе Redis приложение продолжает выполнять перенаправления через PostgreSQL, что сохраняет основную пользовательскую функцию ценой увеличения времени обработки и возможной потери части внутренних счетчиков.
